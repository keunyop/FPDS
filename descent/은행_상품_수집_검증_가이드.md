# 은행 상품 수집 결과를 읽는 법

FPDS Admin에서 확인할 숫자는 세 가지다. **원문 확보 수**는 은행에서 읽어 온 문서 수, **검증 통과 수**는 필수 근거를 갖춘 상품 후보 수, **실제 승인 수**는 상품 원본에 반영한 수다. 여러 문서가 상품 하나를 입증할 수 있고, 정상적으로 끝난 실행에서도 승인 수는 0일 수 있다.

## 수집을 시작할 때

Banks에서 국가·은행·상품 유형을 확인한다. 등록된 상세 출처로 다시 확인할 때는 일반 수집을 사용한다. 은행이 사이트를 개편했거나 상품 상세 주소 자체가 바뀌었을 때는 상세 수집으로 출처부터 찾는다. 이미 진행 중인 같은 범위가 있으면 Runs에서 그 실행을 확인한다.

## 공식 문서를 고르는 예

정기예금 상품 페이지에 “12개월”과 금리만 적혀 있고 아래에 “GIC redemption terms”와 “Rewards redemption terms”가 함께 있다고 하자. 첫 링크는 **예금의 중도해지 약관**이다. 둘째는 **포인트 교환 조건**이다. 은행 주소가 같아도 예금의 해지 가능 여부를 판단할 때 사용할 문서는 첫 번째다.

약관에 “만기 전 해지 불가”라고 적혀 있으면 그 상품의 조기 인출 금지를 기록한다. “30일이 지나면 해지 가능”이라면 대기 기간과 함께 이자 차감·수수료 등의 실제 조건을 확인한다. “첫 30일은 해지 불가”만 있고 그 이후의 조건이 없으면 원문에서 확인할 수 있는 범위까지만 판단한다. 같은 상품에 적용되는 예외가 불분명하면 필수 조건 미확정으로 남긴다.

카드에서는 구매 금리와 현금서비스 금리를 각각의 표제·값·연 이율 설명과 함께 읽는다. 같은 카드명에 일반 공백과 줄 바꿈 방지 공백이 섞인 경우는 같은 표기를 확인할 수 있지만, 이름에 **Plus**가 붙은 다른 카드의 행까지 합치면 안 된다. 입출금계좌의 “월 10달러, 잔액 조건 충족 시 면제”도 기본료와 면제 조건을 함께 읽는다. [상품별 문서와 승인 규칙](../docs/03-design/collection-accuracy-policy.md)

## 승인 수가 예상보다 적을 때

Runs에서 국가·은행·유형과 실행 번호를 먼저 확인한다. 조사 순서는 다음과 같다. 상세한 근거는 비공개 실행 기록과 저장 원문에서 확인한다.

| 처음 멈춘 곳 | 확인할 내용 | 그다음 할 일 |
|---|---|---|
| 상세 출처 확보 | 공식 주소가 특정 상품을 여는지, 이동 후 국가·언어가 맞는지 | 출처가 바뀌었으면 해당 은행·유형만 다시 탐색한다. |
| 캡처·파싱 | 이번 실행의 스냅샷과 체크섬, 실제 파일 형식, 표와 각주가 남아 있는지 | PDF로 표시된 오류 응답을 약관으로 사용하지 않는다. 파서 수정은 같은 보존 원문으로 먼저 검증한다. |
| 필수 근거 보강 | 빠진 필드, 상세에서 관찰한 링크, 선택된 주소와 종료 사유 | 공식 링크 소진, 예산 소진, 문서 읽기 실패를 구분한다. 은행이 해당 사실을 미공개했다고 단정하지 않는다. |
| 값 검증 | 상품명, 통화, 표의 행·열, 인용문 주변의 예외와 단위 | 필수 사실이 불명확하면 제외 사유를 확인한다. 선택 항목만 비었으면 추가 실행할 필요가 없다. |
| 상품 원본 반영 | 자동 검증 수와 실제 승인 수, 저장 단계의 제외 사유 | Changes에서 신규·변경 이력을 확인한다. 같은 값 재확인은 새 버전을 만들지 않을 수 있다. |

## 수집 품질을 비교할 때

같은 국가·은행·상품 유형과 같은 원문으로 변경 전후를 재생한다. 해당 문서를 고른 횟수, 정확한 필수 값을 얻은 상품 수, 잘못된 상품·금액·조건을 거부한 수를 함께 본다. 실은행 결과를 보고할 때는 실행일, 시도한 범위 수, 성공적으로 읽은 문서 수, 근거 누락으로 제외한 후보 수, 실제 승인 수를 구분한다. 하나의 은행에서 재현한 결과를 전체 은행의 성공률로 환산하지 않는다.

## 이번 개편에서 재현한 사례

TD Cash Back Visa 카드의 보존 원문에는 구매 금리 **21.99%**, 현금서비스 금리 **22.99%**, 연회비 **0**이 따로 적혀 있다. 은행 페이지가 상품명 안의 공백을 HTML로 두 번 인코딩해, 종전에는 금리가 같은 카드에 속한다는 확인에 실패했다. 같은 원문을 다시 처리하자 세 값이 각자의 항목으로 자동 검증을 통과했다. 다른 카드명이 들어간 대조 사례는 계속 제외된다. 이 수치는 보존본을 재생한 결과다. 두 상품 상세가 같은 은행 요금표로 연결되는 경우도 검사한다. 실행에 문서 한 개를 더 받을 여유만 있어도 해당 주소는 한 번만 선택하고, 각 상세에서 링크를 관찰한 스냅샷을 따로 남긴다. 같은 요금표를 발견한 사실만으로 두 상품에 같은 가격을 넣을 수는 없다. [문서 선택과 출처 연결 테스트](../api/service/tests/test_collection_evidence_research.py)
