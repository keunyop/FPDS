# SwitchaBank Public 성장 기능 제안


## 1. 제안의 핵심

먼저 금리 의미와 정보 기준일을 바로잡고, **검색 목적별 비교 페이지 → 유지되는 비교 목록 → 같은 조건의 금액 차이 계산 → 은행 공식 페이지 확인** 흐름을 강화한다. 이후 저장한 비교를 다시 확인할 이유를 만든다.

첫 실험은 캐나다 Savings·Chequing·GIC 중 비교 조건을 충분히 검증할 수 있는 부분에 집중한다. 미국과 카드·대출은 현재 제공을 유지하면서 데이터 충실도와 사용 결과를 보고 성장 투자를 넓히는 편이 합리적이다. 이는 상품 범위를 줄이거나 새 국가를 추가하자는 제안이 아니다.

체류 시간은 사용자가 조건을 이해하고 비교하는 데 쓴 시간으로 해석한다. 정확한 답을 빨리 얻고 은행으로 이동해 체류 시간이 줄어도 성공일 수 있다. 핵심 성과는 유효한 정보에 기반한 은행 이동 증가이며, 클릭은 실제 계좌 개설이나 대출 실행을 뜻하지 않는다.

검색량, GA4, Search Console 실적, 실제 방문자 행동 데이터에는 접근하지 않았다. 아래 우선순위는 관찰된 사용 마찰·재사용 가능한 코드·데이터 준비도에 따른 제품 가설이며 트래픽 증가율 예측이 아니다.

## 2. 조사 범위와 현재 자산

루트 README → 개발 저널 → 문서 지도 순으로 읽고, Public README, 요구사항 FR-PUB-020~023, scope baseline, 관련 WBS/결정/RAID, 디자인·Public IA·지표·다국어 정책을 확인했다. 실제 구현은 Public 라우트, finder, 비교, 상세, 계산기, SEO, sitemap, analytics 및 API의 금리 직렬화·freshness 로직을 중심으로 읽었다.

Production은 홈, 예금, 카드, 대출, 상세 2개, Methodology, 미국 홈을 Chrome으로 확인했다. EN/KO/JA와 1440px·768px·정확한 390px를 포함했다. 공개 API 전체 216개 상품도 읽었다. 운영 분석에 테스트 클릭이 섞이지 않도록 브라우저의 engagement/feedback 전송과 Google Analytics 요청을 차단했다. 비공개 Admin 로그인, 피드백 제출, 수집, 수정, 배포는 실행하지 않았다.

## 3. 성장 기능보다 먼저 해결할 문제

### B. 스냅샷 성공과 상품 정보의 최신성이 섞임 — 확인됨

9월 16일 읽은 CA 8월 27일·US 9월 3일 스냅샷은 모두 `status=fresh`였다. `build_freshness_payload`는 stale flag 또는 후속 refresh 실패를 보며, 경과 시간을 판단하지 않는다. 오래된 성공 스냅샷을 넣은 직접 함수 확인에서도 `fresh`였다.

현재 UI 문구는 `Current snapshot`이므로 실시간 금리라고 명시한 것은 아니다. 다만 녹색 확인 표시·순위·과거 검증일이 함께 쓰여 방문자가 최신성의 의미를 잘못 이해할 여지가 있다.

권고: 스냅샷 생성일과 상품별 마지막 확인일을 분리하고, 허용 확인 주기·만료 조건을 상품군별로 정한다. 운영자가 확인할 지연 목록과 검수 주기를 만든다. D-069의 수동 수집 결정을 존중하며 이번 제안이 자동 수집 재개를 승인하는 것은 아니다. 스냅샷만 다시 생성했다고 은행 사실을 새로 검증한 것처럼 표시해서도 안 된다.

근거: [freshness API](../../api/service/api_service/public_common.py), [상태 UI](../../app/public/src/components/fpds/public/public-freshness.tsx), [결정 D-069](../00-governance/decision-log.md).

### C. 비교 조건과 계산 가정의 부족 — 일부 확인, 추가 검증 필요

현재 Home Deposit Top 5에는 Savings와 GIC가 함께 나오고, finder는 동일 Product Type과 한 숫자를 비교한다. 후보 선별에는 별도의 통화·GIC 만기·프로모션 적용기간 검증이 없다. 이는 모든 결과가 잘못됐다는 뜻은 아니지만 더 높은 숫자만으로 교체의 이점을 설명하기 어려운 구조다.

공개 INDEXED GIC에는 대표 금리 5%, 기간 텍스트 18개월, 5년 금리표 행이 동시에 있었다. 원본 전체 사실을 이번 조사에서 확정하지 못했으므로 어느 값이 정답이라고 단정하지 않는다. 다만 이 상태를 동일 만기 순위나 확정 수익 계산에 쓰기 전 검토가 필요하다.

예금 계산기는 `금액 × 표시 연 금리 × 기간/365`의 단리 추정이다. Oaken Savings에서는 최소 잔액 0이 초기 금액으로 선택돼 실제 화면이 `0 → 예상 이자 $0.00`으로 시작했다. 만기가 없으면 1년을 쓰므로 프로모션 종료일·구간별 금리·복리·APY를 정교하게 반영하는 계산기는 아니다.

권고: 상품별 확정 금리 의미와 적용 기간을 먼저 확보하고, 계산 불가 사례는 불가 사유와 공식 확인 경로를 제공한다. 기존 finder의 단일 지표 규칙 변경은 FR-PUB-021 변경으로 명시한다.

### P1-1. 검색 목적별 전용 비교 페이지

지금은 `/products`, `/cards`, `/loans`라는 넓은 카테고리와 개별 상품 페이지가 중심이다. 검색·필터 URL은 의도적으로 `noindex`다. 따라서 필터 기능이 있다는 사실만으로 구체적인 검색 질문에 맞춘 진입 페이지가 생기지는 않는다.

첫 후보는 다음 세 가지다. URL은 예시이며 경로 체계는 구현 시 확정한다.

- `/ca/savings-accounts`: CAD Savings의 기본 금리·프로모션·인출 조건을 구분하는 비교.
- `/ca/no-monthly-fee-chequing`: 기본 월 수수료 0과 잔액·입금 조건 충족 시 면제를 분리하는 비교.
- `/ca/1-year-gic`: 검증된 1년 행, 통화, 상환 조건이 맞는 GIC 비교. 현재 기간별 데이터가 부족하면 페이지 공개를 미룬다.

각 페이지는 고유한 질문의 답, 해당 조건의 상품 표, 비교 가능한 범위, 마지막 확인일, 짧은 설명, 비교 추가, 공식 은행 링크를 함께 제공한다. 홈에도 `월 수수료 비교`, `Savings 비교`, `GIC 기간별 비교`를 바로 노출한다. 보유 상품명을 모르거나 처음 계좌를 찾는 방문자는 기존 finder 입력 없이 시작할 수 있다.

임의 필터 전체를 검색 허용으로 바꾸거나 국가×은행×조건 조합을 대량 생성하지 않는다. curated 페이지에만 자체 canonical·서버 렌더링·sitemap·내부 링크를 적용한다. 승인된 정확한 상품이 충분한지 확인한 뒤 공개한다. 3개 이상 서로 다른 은행의 유효 상품은 초기 비교 품질의 운영 기준 제안이지 Google의 요구사항이 아니다.

검증: Search Console의 해당 URL·비브랜드 검색 노출/클릭, 동의한 GA 방문자의 진입·참여, 같은 기간 은행 이동 건수. 검색 수요와 순위 난도는 실제 GSC 데이터를 보고 조정한다.

근거: [SEO 정책](../../app/public/src/lib/public-seo.ts), [sitemap](../../app/public/src/app/sitemap.xml/route.ts), [Google 필터 URL 가이드](https://developers.google.com/crawling/docs/faceted-navigation). [NerdWallet](https://www.nerdwallet.com/banking/best/high-yield-online-savings-accounts)은 Savings, 기간별 CD, 무료 Checking, 계산기로 진입 경로를 나눈다. 이러한 구조는 참고할 수 있지만 그 사이트의 트래픽 성과를 SwitchaBank 효과로 간주할 수 없다.

### P1-2. 유지·공유되는 비교 목록

가장 구체적으로 재현한 사용 마찰이다. 예금 목록에서 한 상품을 선택하면 `1/4 selected`, Monthly fee 정렬로 바꾸면 `0/4 selected`가 된다. 코드도 상품 응답·쿼리 변경 시 선택을 지운다. 선택한 상품을 현재 목록에서만 찾으므로 단순히 reset 한 줄을 삭제하는 것으로는 충분하지 않다.

권고하는 흐름:

1. 검색이나 정렬을 바꿔도 최대 4개 선택 유지.
2. 상세에도 `비교에 추가` 제공. 같은 은행 관련 상품에 더해 `다른 은행의 같은 유형 비교`로 연결.
3. 별도 비교 URL에 공개 상품 ID·국가·UI 언어만 넣어 비교 공유.
4. 재방문용 저장은 명시적 사용자 액션으로 이 기기에만 저장. 지우기·보관기간·기기 간 미동기화 안내.
5. 방문 때 최신 승인 projection으로 재조회하고 사라진 상품·변경된 조건 표시.

공유에는 실제 잔액, 보유 관계, 입력 금융값을 넣지 않는다. 공개 상품 ID로 된 임의 조합은 `noindex`로 유지한다. 통화·유형이 다르면 비교 가능 범위와 계산 불가를 명확히 표시한다. 은행 간 후보를 임의 종합 점수로 추천하지 않는다.

모바일에서는 `선택 2개 · 비교 보기`가 보이는 작은 고정 영역으로 돌아갈 수 있게 한다. 현재 위쪽에 렌더링되는 비교 패널까지 긴 목록을 다시 스크롤해야 하는 부담을 줄인다.

검증: 필터·정렬·상세 왕복 후 선택 유지, 공유 URL 복원, inactive 상품 처리, 390px에서 비교 접근. 기능 사용량을 추가 계측하려면 FR-PUB-022의 고정 이벤트 계약을 별도로 바꿔야 한다.

근거: [비교 상태](../../app/public/src/components/fpds/public/product-compare-workspace.tsx), [같은 은행 관련 상품 조회](../../app/public/src/app/products/[productId]/page.tsx).

### P1-3. 같은 금액·기간의 차이 계산

이미 있는 단일 상품 계산기를 발전시킨다. 사용자가 선택한 두 상품에 같은 가상의 금액·기간을 적용해 `예상 이자`, `공개된 고정 수수료`, `계산 가능한 범위의 차이`를 나란히 보여준다. 개인에게 최적 상품을 판정하는 기능과 분리한다.

예: 실제 상품과 무관한 단리 예시로 CAD 20,000을 1년간 연 2%와 3%에 예치하면 이자는 각각 CAD 400·600, 차이는 CAD 200이다. 이는 세금·수수료·복리·금리 변동을 제외한 가정 계산이다. 금액 차이가 보이면 금리 숫자만 볼 때보다 은행 조건을 확인할 이유가 분명해진다.

첫 버전은 동일 통화의 무조건 고정 월 수수료 비교와, 기간·연율 의미가 검증된 단순 예금에 제한한다. GIC는 실제 선택한 만기 행을 사용한다. 프로모션·금액 구간·보너스·중도해지·환전·APR/APY를 계산하려면 해당 계약과 승인 데이터부터 확보해야 한다. 누락된 비용을 0으로 간주해 `순이익`이라고 표시하지 않는다.

입력 금액은 브라우저 안에서만 처리하고 URL·GA·운영 집계·저장 비교에 보내지 않는다. finder의 보유 상품 입력에 금융값을 섞지 않는다. 별도 계산기 화면과 계산식·반올림·경계·계산 불가 규칙을 승인받는 구현 범위다.

검증: 사용자가 두 상품의 차이와 제외 조건을 설명할 수 있는지, 계산 후 공식 페이지 이동이 늘어나는지. 0·누락·만기 불일치·통화 불일치·만료 프로모션·APY 사례를 회귀 검증한다.

### P1-4. 은행으로 이동하기 직전의 확인 패널

현재 공식 링크는 이미 충분한 위치에 존재한다. 링크 개수를 더 늘리기보다 `이 상품의 조건을 이해했으니 은행에서 확인하겠다`는 결정을 돕는다.

- 버튼: `은행에서 최신 조건 확인`처럼 이동 목적과 외부 사이트임을 명시.
- 옆 정보: 통화, 핵심 비용·금리 조건, 상품 마지막 확인일, 확인된 공식 도메인.
- 확인할 항목: 해당 상품에서 실제 공개된 최소 금액, 면제 조건, 인출 제한. 없으면 은행에서 확인하도록 표시.
- 모바일 상세·비교 하단: 제품명과 공식 이동 버튼이 있는 간결한 고정 액션. 내용을 가리거나 consent·키보드·비교 바와 겹치지 않게 배치.
- 상품 공식 URL의 실패·다른 상품 리다이렉트를 운영자가 확인할 수 있는 점검 결과.

이동을 막는 강제 팝업이나 여러 단계 확인을 추가하지 않는다. `신청 가능`, `승인 보장`, 실제 신청 화면이 아닌데 `즉시 개설` 등의 표현을 쓰지 않는다. 신청 서류나 세부 자격은 승인된 데이터가 없으면 생성하지 않는다.

추가 관찰: 390×844 예금 목록에서 첫 상품 수치는 약 y=852, 첫 공식 이동은 약 y=912에 있었다. 홈의 상품명 입력·실행 버튼도 첫 화면 아래였다. 문서 가로 넘침은 없었지만 목적 바로가기와 짧은 첫 화면 구성은 실험 가치가 있다. 이 측정은 한 브라우저 관찰이지 사용자 이탈의 증명은 아니다.

### P2-1. 비교에 연결되는 다국어 설명 콘텐츠

범용 금융 뉴스를 많이 발행하기보다 실제 비교 화면에서 생기는 질문을 다룬다. 예: 기본 금리와 프로모션 금리의 차이, 월 수수료 면제 조건 읽는 법, GIC 만기와 중도 인출, 캐나다 계좌 이전 시 확인할 항목.

짧은 EN/KO/JA 설명 → 관련 공개 비교 표 → 계산 또는 비교 목록 → 은행 공식 확인으로 연결한다. 상품을 보유하지 않은 신규 방문자를 위한 출발점도 제공한다. 한국어·일본어 이용자의 비교 수요는 유망한 가설이지만 언어별 실제 유입을 확인하기 전 우선 시장이라고 확정하지 않는다.

현행 source-language 정책상 은행 상품명·조건을 자동 번역한 것만으로 KO/JA 상품 URL을 검색 허용해서는 안 된다. 직접 작성·검수한 설명 페이지를 별도로 만들고, 상품 고유 조건의 번역이 필요하면 그 범위를 별도 승인한다. 운영 주체·편집/검수 방법·정정 정책을 사실대로 설명하되 존재하지 않는 전문가나 인증을 만들지 않는다.

[Google의 콘텐츠 안내](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)는 독자에게 유용한 정보, 명확한 출처와 작성 주체를 강조한다. 금융 정보에서는 특히 신뢰를 우선해야 한다. 특정 콘텐츠 형식이 검색 순위를 보장하는 것은 아니다.

### P2-2. 저장한 상품의 승인된 변경 요약

사용자가 다음 주 다시 와서 `저장한 비교의 조건이 바뀌었는가`를 확인할 수 있게 한다. 처음에는 서버 계정 없이 로컬 비교 저장부터 제공하고, 새로 읽은 승인 값이 저장 당시와 다른지 알려주는 방식이 작다.

사이트 공통 변경 이력은 별도 public-safe 이력이 필요하다. 현재 보존 정책은 국가·범위별 최근 완료 스냅샷 두 개뿐이다. 현재 저장분으로 1년 금리 차트를 만들 수 있다고 가정하면 안 된다. `last_changed_at`도 금리만 바뀐 시각이라고 단정할 수 없다.

이력을 추가할 경우 공개 승인된 금리·수수료·유효기간 변화만 보관하고, 관측 시점과 실제 효력 발생일을 구분한다. 내부 리뷰 코멘트·증거·정정 흔적을 그대로 Public에 노출하지 않는다. 기록이 없는 기간을 보간해 채우지 않는다.

근거: [보존 정책](../03-design/bounded-data-retention-policy.md).

### P3. 동의 기반 알림

금리 변경·프로모션 종료 알림은 재방문 이유가 강하지만 지금 바로 첫 기능으로 만들기에는 선행조건이 많다. 신뢰할 수 있는 갱신 주기, 공개 변경 이력, 승인된 종료일, 이메일/구독 동의·해지·보관·발송 운영이 필요하다.

수집이 수동이고 오래된 데이터도 fresh인 상태에서 알림부터 만들면 늦거나 잘못된 안내를 자동으로 보내게 될 수 있다. 비교 저장 사용과 재방문 수요를 먼저 확인한 뒤, 명시적인 별도 범위로 검토한다. 이번 조사에서는 구독자를 수집하거나 메시지를 발송하지 않았다.

## 5. 측정과 실험 설계

현행 first-party 집계는 `product_detail_click`, `official_bank_click`, `finder_product_selected` 세 종류의 일별 국가/상품 합계다. 방문자·세션·진입면·노출 수가 없어 단계별 퍼널이나 순 방문 전환율을 계산할 수 없다. 공식 클릭을 상세 클릭으로 나눈 값도 홈·목록 직접 이동을 포함하므로 상세 전환율이 아니다.

GA4는 동의한 방문자에게만 활성화되며 현재 정책은 페이지 조회 중심이고 상품 클릭·전환 이벤트를 보내지 않는다. 따라서 전체 first-party 클릭 수를 동의한 GA 세션 수로 나눠 전환율이라고 제시해서는 안 된다.

| 목표 | 지금 활용 가능한 지표 | 추가 승인이 필요한 계측 |
|---|---|---|
| 검색 유입 | GSC URL·검색어별 노출/클릭, 비브랜드 유입; 계정 실적은 미확인 | 별도 수집 없이 실제 보고서 검토 가능 |
| 유용한 체류 | 동의한 GA 방문자의 활성 참여 시간·페이지 탐색 | 비교 열기·계산 사용·공유 복원에 대한 제한된 행동 집계 |
| 은행 이동 | 동일 기간·국가·상품별 official_bank_click 건수 | 표면별 공식 CTA 노출과 클릭의 동일 모집단 집계 |
| 재방문 | 동의한 GA의 재방문 지표, 제공 범위 확인 필요 | 저장 비교 재열기 일별 합계; 고유 사용자 유지율로 부르지 않음 |
| 신뢰 | 기존 오류 신고와 공개 데이터/공식 링크 검수 | 정확성·경과일·불가 계산 상태의 운영 체크 |

향후 최소 계측안은 고정 이벤트·한정된 화면 분류·일별 합계다. 금액·보유 상품 관계·자유검색·이메일·새 방문자 ID는 전송하지 않는다. 새 이벤트와 노출 집계는 D-071/FR-PUB-022 및 API 검증 계약을 함께 변경하는 별도 승인 범위다. `클릭/노출`도 반복 이벤트를 포함하는 이벤트 비율임을 표시하고 실제 가입률로 부르지 않는다.

GA의 참여 시간은 페이지가 활성화된 시간을 측정하므로 새 탭으로 은행을 연 뒤 남아 있는 SwitchaBank 탭의 경과 시간과 다르다. [Google Analytics 참여 시간 정의](https://support.google.com/analytics/answer/11109416?hl=en).

실험 순서:

1. 금리 의미·freshness 결함을 재현하고 수리 범위를 먼저 결정. 잘못된 정보를 유지하는 A/B 테스트는 하지 않는다.
2. 기존 GSC·GA·운영 집계에서 가능하면 최근 28일 기준선을 확보한다. 부족하면 새로 모으되 기준선 부재를 명시한다.
3. 예금 목적 페이지 3개 이하와 비교 선택 유지·공유를 첫 성장 묶음으로 검토한다. 화면 실험 효과를 구분하려면 순차 출시한다.
4. 사용성 관찰로 보유 상품을 모르는 신규 방문자와 정확한 상품을 아는 방문자가 각각 비교와 은행 이동을 완료하는지 확인한다.
5. 데이터가 충분한 상품만 차이 계산을 추가한다. 이후 이동 패널을 실험한다.
6. SEO는 색인·질의 노출·클릭 추이를 몇 주에 걸쳐 본다. 트래픽이 적으면 짧은 실험의 통계적 승리를 선언하지 않는다. 전후 비교는 금리·시즌·유입 변화의 영향을 받으므로 인과 효과로 단정하지 않는다.

숫자 목표와 실험 표본 수는 현재 유입·기준 전환율을 확인한 다음 정한다. 현재 근거로 방문자 몇 배, 체류 몇 분 증가를 약속할 수 없다.

## 6. 범위·운영 판단

기존 구성요소 재사용이 많은 항목은 비교 상태 유지, 상세 비교 진입, 공식 이동 패널이다. 그래도 이번 요청은 분석·제안이므로 구현하지 않았다.

별도 설계·승인 경계를 갖는 항목:

- 전용 검색 페이지: FR-PUB-020의 검색 허용 경로 추가. 모든 필터의 noindex를 해제하지 않는다.
- finder 조건 변경: FR-PUB-021의 동일 유형·한 지표 의미를 명확히 수정. 개인 프로필 순위로 확대하지 않는다.
- 계산 확대: 입력 처리, 공식 금리 의미, 계산·제외 조건에 대한 계약 필요.
- 로컬 저장: 저장 항목·만료·삭제·사용자 설명을 결정. 계정/보유 자산 정보 저장으로 확대하지 않는다.
- 이벤트 확대: FR-PUB-022의 제한된 수집 범위를 변경.
- 금리 이력·알림: 새 public-safe 데이터 보존, 동의·발송 운영 계약 필요.
- 최신성: 허용 경과일과 운영 절차를 정하되 자동 수집 복구는 D-069 변경 없이 시행하지 않는다.

우선순위가 낮은 제안은 범용 AI 금융 챗봇, 복합 개인화 점수, 카드 보상액 추천, 커뮤니티/사용자 평점, 새로운 국가의 대량 추가, 장식용 실시간 차트다. 데이터·운영·검증 부담이 크거나 현행 공개 필드로 약속하기 어렵다. 기존 브랜드·디자인 시스템을 유지하면서 구체적 비교 행동을 먼저 개선한다.

## 7. 검증 기록과 한계

- Production 공개 API: CA 165개 + US 51개 전체 조회; 국가·유형·필드 충실도·기준일 확인.
- Chrome: 9개 화면/국가/언어 조합 확인, 1440/768/390px에서 관찰 화면의 문서 가로 넘침 없음, 수집한 JavaScript exception 없음. 전체 접근성·성능 인증은 아님.
- 390×844 추가 확인: 홈, 예금, Savings 상세의 실제 접기 전 위치와 계산기 0 초기값 확인.
- 비교 선택 유지: 실제 `1/4 → Monthly fee 정렬 → 0/4` 재현.
- API 실제 함수: BMO 문장형 가산금리 추출과 오래된 성공 스냅샷 fresh 반환 재현. 전체 런타임 테스트는 실행하지 않음.
- 기존 Production SEO audit 통과: 사이트맵 225개 URL + 대표 경로 10개. HTTP 응답·canonical·metadata·robots·hreflang·구조화 데이터·중복 등을 검사했으며 Google 실제 색인·순위를 증명하는 것은 아님.
