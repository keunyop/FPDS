# 히고은행·가고시마은행 상품팩토리 저장안

2026-11-27 기준. 대상은 FPDS의 일본 두 은행과 테스트 상품팩토리다. 히고은행과 가고시마은행을 자기 기관을 모기관으로 두는 독립 기관으로 개설했다. [테스트 상품팩토리](http://ec2-57-181-66-85.ap-northeast-1.compute.amazonaws.com/pf/)

## 독립 기관 개설

관리자 매뉴얼 §8.1(본문 75~76쪽, PDF 82~83쪽)은 모기관이 없는 기관의 모기관 필드에 자기 기관코드를 입력하도록 명시한다. 관리자 오퍼레이션가이드 §2.1(9쪽)의 경로는 **설정 → 기관 → 추가(+) → 입력 → 저장**이다. 두 은행을 각각 모기관으로 운영하므로 모기관여부를 체크한다. 기본값은 체크 해제다.

| FPDS 은행코드 | PF 기관코드 | 기관명 | 모기관 | 모기관여부 |
|---|---|---|---|---|
| HIGO | HIGO | 肥後銀行(Higo) | HIGO | 체크 |
| KAGOSHIMA | KAGO | 鹿児島銀行(Kagoshima) | KAGO | 체크 |

기관코드·모기관코드는 8바이트, 기관명은 100바이트 범위다. FPDS의 KAGOSHIMA는 영문 9바이트이므로 PF의 KAGO에 매핑한다. 기관 관리와 로그인 목록에서 위 등록 결과를 확인했다. 관리자 매뉴얼의 적용시작일 기본값은 등록 당일 00:00:00, 종료일 기본값은 9999-12-31 23:59:59다. 이번 설치본의 기관 화면에는 적용일자 입력란이 없다.

저장 후 각 기관으로 로그인해 표시 기관과 템플릿 담당자의 역할·메뉴·조건 편집 권한을 확인한다(관리자 오퍼레이션가이드 §2.2, 10~12쪽 이후). 그다음 두 기관에서 기존 코드와 채번규칙을 조회하고 공통 정의표의 첫 조건·조건군·상품템플릿을 구성한다(§2.5, 33쪽 및 §3.1~3.3, 55·67·82쪽부터). 기관 화면의 복사는 선택한 기관 행을 복제한다. 독립 기관 사이의 템플릿 원본 공유나 동기화는 이 절차에서 확인되지 않는다. 단일 공통 정의표에 표준 코드, 두 은행의 PF 코드, 버전을 연결하고 변경 시 양쪽 정의의 일치 여부를 검사한다.

## 실제 조회 결과

기관 등록 전 로그인 목록에는 표준은행(STDA)과 Admin(000)이 표시됐다. STDA 로그인에 성공했고 응답의 상위기관도 STDA였다. STDA 계정에 기관 관리 쓰기 권한이 있었다. 상품·조건 템플릿 화면은 로그인 기관과 상위기관이 일치하고 쓰기 권한이 있을 때 템플릿 편집을 허용한다. 아래 STDA 코드는 공통 정의 설계의 비교 자료다.

| STDA 템플릿 | 코드 | 연결 항목 | 연결된 조건그룹 예 |
|---|---|---:|---|
| 보통예금 普通預金 | 0110001 | 16 | 003 가입자격, 004 요구불계약, 010 예금금리 |
| 정기예금 定期預金 | 0130001 | 16 | 003 가입자격, 006 거치식계약, 010 예금금리 |
| 주택대출 住宅ローン | 0210003 | 10 | 030 대출계약, 037 상환, 040 중도상환, 045 대출금리 |

정액적립정기예금(0120001), 자유적립정기예금(0120002), 프리론(0210001), 사업자대출(0231001)도 목록에서 확인했다. 모두 STDA 코드다. 개별 은행 상품에 어떤 템플릿을 연결할지는 계약 성격과 조건 집합을 대조해 결정한다. 예컨대 보통예금의 010은 금리 **그룹**이므로 한 상품의 금리 조건코드 자리에 입력할 수 없다.

## 저장 순서

| 순서 | FPDS 원천 | 상품팩토리에 저장하거나 연결할 항목 |
|---|---|---|
| 1. 기관 | JP 및 HIGO·KAGOSHIMA | 발급된 PF 기관 HIGO·KAGO를 FPDS 은행코드와 연결한다. |
| 2. 공통 정의 | 예상표 수신·여신, 8개 상품템플릿, L/R/I/F 조건 64개 | 양쪽 기관에 공통 정의표의 상품분류·개별 조건·조건군·상품템플릿을 대응시킨다. 단위·선택지·허용범위가 일치하는 기존 정의를 재사용하고 기관별 채번 결과를 기록한다. |
| 3. 은행별 상품 | 승인된 현재 상품 버전의 상품 ID, 은행, 원어명, 유형, 통화 | 은행별 PF 상품코드와 공통 상품템플릿을 연결한다. FPDS 상품 ID와 PF 환경·기관·상품코드의 대응을 보관한다. 예상표 P번호는 대조용으로 쓴다. |
| 4. 조건값 | 승인 버전에 연결된 필드값과 근거 | PF 상품코드, 조건그룹 템플릿·그룹·조건코드를 지정하고 유형별 값과 적용 구간을 설정한다. 통화·단위·적용기간·근거 원문은 FPDS 버전까지 역추적할 수 있게 한다. |
| 5. 재수집 | FPDS 승인 버전과 변경 이력 | 최초 버전은 신규 등록, 변경은 같은 PF 상품의 조건 개정으로 처리한다. 버전·매핑 개정번호와 PF 재조회 결과를 기록한다. 실패한 항목만 재시도하고 수집 누락·제외는 판매중지로 전송하지 않는다. |

## 조건값 변환

### 반복 적재 준비 구현과 두 은행 pre-flight

개발 DB에 마이그레이션 0050을 적용했다. 공통 템플릿 8개·조건 64개·목록 선택지 94개·템플릿 조건 연결 159개를 등록했다. 활성 상품의 현재 승인 버전과 동일 버전·동일 은행의 필드 근거를 읽는 뷰 2개를 만들었다. 은행별 비공개 명령은 공통 코드, 승인 버전 ID, 변환 조건값, 나머지 검증 필드와 미산출 조건을 JSON Lines로 출력한다. 일본 Worker가 발급한 검증 버전을 Admin 자동승인·자동제외·근거평가가 인식하도록 수정했다. [조회 명령과 현재 변환 범위](../../api/service/README.md#pf-collection-channel)

개발 DB의 16개 활성 범위를 로컬 수집 코드로 확인했다. 히고는 개인·법인 관련 5개 목록·보조 주소에서 접근 거부가 반환됐다. 가고시마는 개인 6개 유형에서 각각 결제성예금 3개, 저축예금 1개, 정기예금 9개, 주택대출 2개, 개인대출 8개, 한도대출 3개의 이름이 붙은 PDF를 찾았다. 유형별 표본 1건씩 총 6건을 읽었다. 여신 3개 표본에서 은행·상품 식별이 일치했고 예금 3개 표본에서는 기존 Worker 근거 규칙으로 식별이 확정되지 않았다. 법인 목록은 열렸고 현재 이름 대조 경로에서 두 법인 유형의 PDF는 0건이었다. 카드론 S 상환계좌 불필요형의 원문과 검증 표본의 체크섬이 일치했고, 실제 원문에서 한도 및 8개 금리 구간을 변환했다. 개발 DB의 상세 출처·JP Run·정식 상품·PF 조회 상품은 모두 0건이다.

### FPDS 선행 점검 결과 (2026-11-27)

개발 DB를 읽기 전용으로 조회했다. JP·HIGO·KAGOSHIMA가 활성이고 공식 목록 범위는 은행별 8개다. 두 은행의 등록 상세 출처·정식 상품과 JP 수집 실행은 모두 0건이다. 배포 Worker에서의 수집 및 DB 반영은 미검증이다.

로컬 FPDS 조회기로 가고시마의 현재 종합 목록을 읽어 6개 유형의 상품명과 PDF 링크 26건을 식별했다. 한도대출 범위의 3건에는 카드론 S의 상환계좌 불필요형과 인출형이 각각 있다. 불필요형의 현재 PDF 체크섬은 8개 연이율 구간을 검증한 회귀 원문과 일치했다. 같은 환경에서 히고 공식 목록은 접근 거부, 보통예금 PDF는 HTTP 403이었다. 일본 전용 Worker 테스트 8건과 API 테스트 1건을 통과했다.

PF를 기다리는 동안 먼저 가고시마 한도대출 단일 범위를 상세 수집해 현재 원문·자동 승인 또는 제외 사유·정식 상품 버전·필드 근거의 연결을 검증한다. 정식 버전이 생기면 PF 쓰기 없이 기관코드·상품 ID와 버전·조건코드·단위·구간 경계·근거 참조가 있는 변환 결과를 대조할 수 있다. 히고는 배포 Worker에서 허용된 공식 목록과 PDF의 본문 확보부터 확인한다.

### 유형별 변환 규칙

- **L 목록** — PF 조건템플릿에서 목록 키·표시명과 단일 선택 여부를 지정할 수 있다. 승인된 값만 PF 선택코드에 대응한다. 가입 채널이 둘이면 복수 선택을 보존한다.
- **R 범위** — 템플릿이 허용하는 입력 범위와 상품의 계약 한도를 구별한다. 최저·최고 가입금액이 각각 공시되면 별도 조건값으로 관리하고 각각 통화와 단위를 유지한다.
- **I 금리** — 단일 금리는 해당 조건값으로, 한도·만기·채널에 따라 달라지는 금리는 각 구간과 결과 금리를 복합조건의 행으로 저장한다. PF 화면 구현에서 금리값·기준금리와 복합조건 행 구성을 확인했다. 승인 버전에 요약문만 있으면 공식 근거와 대조해 구조화한 뒤 전송한다. 적용일은 확인일로 대신하지 않는다.
- **F 수수료** — PF에는 금액과 요율 입력이 있다. 건당 엔화, 원금 대비 비율, 명시적 면제를 구별한다. 화면이 일부 빈 숫자에 0을 표시하므로, 공시되지 않은 선택값은 전송 대상에서 제외한다. PF가 필수로 요구하는 미공시 값은 해당 상품의 연계를 보류하고 사유를 남긴다.

상품 화면의 엑셀 업로드는 이미 선택된 기관·상품·조건그룹·조건코드와 복합조건 표를 대상으로 한다. 예상표 전체에서 기관, 템플릿, 상품을 한꺼번에 생성하는 경로는 확인되지 않았다. 정기 연계는 FPDS 승인 완료 후 별도의 서버 작업으로 실행하고, 지원되는 PF 쓰기 인터페이스와 버전 처리 방식을 확정한다. FPDS의 승인과 PF 저장·판매개시는 별개로 관리한다.

## 첫 검증

1. 두 은행에서 같은 공통 정의에 대응하는 템플릿·조건을 조회하고 각 기관 상품의 값이 독립적으로 저장되는지 확인한다.
2. 요구불예금 하나와 가고시마 카드론 S의 상환계좌 불필요형으로 단일값·복합값을 검사한다. 카드론 원문 회귀 표본의 한도 50만 엔은 연 14.8%, 50만 엔 초과~100만 엔 이하는 연 13.15%다. 한도 경계, 8개 구간, 상환계좌형 구분을 재조회해 승인 버전과 비교한다.
3. 동일 버전 재전송 시 중복 상품·조건이 생기지 않는지, 금리만 바뀐 후속 버전에 종전 적용기간이 보존되는지, 미공시 수수료가 0으로 생성되지 않는지 확인한다.

STDA 읽기 조회, FPDS 일본 수집 회귀 테스트 3건과 두 독립 기관 등록을 완료했다. 신규 기관에 대한 계정 로그인·편집 권한과 상품 쓰기 검증이 남아 있다. 예상표 73개는 수집 계획이다.
